# Fedora RPM repository

A self-hosted RPM repository for Bitwarden, Citrix Workspace and Rambox. The
updater downloads the vendors' RPMs, preserves their contents and any upstream
signatures, and publishes the metadata that DNF needs to install and update them.
It does not build these applications or re-sign their packages.

Use it on a Fedora server, virtual machine or container to host your own RPM
repositories. Each service is installed separately and shares a common engine.
The setup guide uses Apache and an example domain. Hosting, HTTPS, backup strategy
and timezone are deployment choices; Proxmox and Cloudflare are optional.

## How an RPM repository works

### Shared engine, separate services

Each application has its own directory, discovery script, installer and Python
update script. The shared engine handles downloads, RPM checks, retention, locking and
metadata publication. Service registration is automatic: a directory with a
valid `service.json` and `service.py` is enough; there is no application list to
edit in the common code.

| Layer | Files | Responsibility |
| --- | --- | --- |
| Common engine | `common/engine.py`, `common/models.py`, `common/http.py` | Download validation, three-version retention, readable filenames and safe publication |
| Service discovery | `services/<id>/service.py` | Find that application's official RPM URLs, checksums, sizes and revisions |
| Service configuration | `services/<id>/service.json` | Allowed RPM names and extra Fedora dependencies |
| Service entry points | `services/<id>/install.sh`, `update.py` | Install or update that application independently |
| Shared installation / CLI | `install.sh`, `rpm_repo_sync.py`, `common/` | Install selected modules and run one service or all installed services |

Each `update.py` runs the complete download, three-version retention and
repository publication process for its own service. Only the common mechanics
(RPM checks, downloads, retention, locking and metadata) are shared.
Scheduling belongs entirely to the administrator through `crontab -e`.

For example, installing Bitwarden does not install Citrix or Rambox
on a new server. Bitwarden and Rambox do not need Citrix's BeautifulSoup dependency.
Existing services retain their modules, state, packages and cron jobs when you
add or update another service. The common engine is a shared dependency and is
updated by the installer; the selected service's vendor code stays separate.

An RPM contains its package name, version, release, architecture, dependencies
and application files. A repository combines RPMs with an index generated by
`createrepo_c`. Apache serves both the packages and that index as ordinary files.

1. The updater discovers the latest compatible RPMs at official vendor sources.
2. It downloads new packages to a private staging directory and validates them.
3. RPM's version comparison selects the newest three versions for each package
   name and architecture.
4. `createrepo_c` generates metadata describing exactly those packages.
5. Packages and metadata objects are published first. `repodata/repomd.xml`, the
   metadata entry point, is replaced atomically after validation.
6. Old versions and duplicate filenames are removed after publication succeeds.
7. A client reads `repomd.xml` and its referenced metadata, compares available
   versions with installed versions, resolves dependencies, and downloads RPMs.

DNF uses the **name and version inside the RPM**, not the downloaded filename,
to decide whether a package is an update. Changes such as Citrix adding `gcc-8`
to an upstream filename therefore do not change its RPM identity. A manually
installed tarball is not tracked by RPM and will not be upgraded by DNF.

Retention counts distinct **epoch/version/release values**, using RPM's native
comparison rather than modification time or alphabetical sorting. A new release
of the same version counts as a distinct retained version. Each architecture
has its own limit. For Citrix, this normally means up to three `ICAClient`, three
`ctxusb`, and three `ctxappprotection` RPMs. A fresh upstream copy replaces a
duplicate of the same version that an older script had re-signed.

Only versions already in the mirror and the newly discovered upstream version
are considered; the updater does not backfill three historical vendor releases
when you create an empty repository.

## Create your own repository server

The commands below run **as root on the Fedora repository server**. Change the
example hostname to your own. On an existing server, preserve its virtual host
and `.repo` files and skip the sections that recreate them.

### 1. Install Apache and obtain the scripts

```bash
dnf install -y httpd git cronie
git clone https://github.com/kbkozlev/fedora-repository.git /opt/fedora-repository
install -d -m 0755 /var/www/html
```

The installer later adds the Python dependencies, `createrepo_c`, RPM tools,
and log rotation. Use Fedora's `/usr/bin/python3`; it includes
the matching Fedora RPM bindings. The supported downloaded architectures are
`x86_64` and `noarch`.

Keep enough free disk space for the retained RPMs, incoming downloads and
temporary metadata. Staging uses hard links where possible and copies when
necessary. Configuration backups do not include another full copy of the RPMs.

### 2. Configure Apache

For a new server, create `/etc/httpd/conf.d/fedora-repo.conf`:

```apache
<VirtualHost *:80>
    ServerName repo.example.com
    DocumentRoot /var/www/html

    <Directory /var/www/html>
        Options Indexes FollowSymLinks
        AllowOverride None
        Require all granted
    </Directory>

    DirectoryIndex disabled
</VirtualHost>
```

Directory listings are useful for browsing packages; DNF itself only needs the
package and metadata URLs. The installer enables listings, disables index-file
selection under `/var/www/html`, and moves an active Fedora `welcome.conf` into
its private backup directory. This removes the default test page at `/`.
For a manual fix before running the installer, disable that configuration and
restart Apache:

```bash
if [ -f /etc/httpd/conf.d/welcome.conf ]; then
    mv /etc/httpd/conf.d/welcome.conf /etc/httpd/conf.d/welcome.conf.disabled
fi
httpd -t
systemctl enable --now httpd
systemctl restart httpd
```

The updater's installer adds `/etc/httpd/conf.d/rpm-repo-sync.conf` with complete
filename columns, natural filename sorting, and cache headers for `.repo` files
and `repomd.xml`. It preserves the virtual host above.

### 3. Publish the HTTP endpoint

Choose an endpoint your clients can reach, such as `https://repo.example.com`.
Configure DNS, HTTPS and firewall access for your deployment. Apache may serve
HTTPS directly or sit behind a reverse proxy or tunnel that handles HTTPS.

With an optional Cloudflare Tunnel, point the public hostname to
`http://localhost:80` if the connector runs on the repository server. If it runs
elsewhere, use the repository server's reachable address, such as
`http://repo.internal:80`. Repository paths must be accessible to DNF without a
browser login or interactive challenge. Test the published URLs from a client.

### 4. Create client repository definitions

Create public directories only for the applications you want to serve. For all
three applications, use the following; omit unused directory names:

```bash
install -d -m 0755 /var/www/html/{bitwarden,citrix,rambox}
```

Create `/var/www/html/bitwarden/bitwarden.repo`:

```ini
[bitwarden]
name=My Repository - Bitwarden
baseurl=https://repo.example.com/bitwarden/
enabled=1
gpgcheck=0
```

Create `/var/www/html/citrix/citrix.repo`:

```ini
[citrix-workspace]
name=My Repository - Citrix Workspace
baseurl=https://repo.example.com/citrix/
enabled=1
gpgcheck=0
```

Create `/var/www/html/rambox/rambox.repo`:

```ini
[rambox]
name=My Repository - Rambox
baseurl=https://repo.example.com/rambox/
enabled=1
gpgcheck=0
```

Use your public hostname in each `baseurl`. The URL points to the directory
containing `repodata/`, not to `Packages/` or the `.repo` file itself. Keeping the
same repository IDs allows an existing client configuration to continue working.

The provided repository definitions use `gpgcheck=0`. Upstream signatures, where
present, are preserved, but this setting does not verify them on the client.
The mirror checks RPM integrity and available upstream SHA-256 checksums.
Client signature verification can be enabled separately with `gpgcheck=1` and
the appropriate vendor keys; there is no custom repository signing key here.

### 5. Install only the services you need

Install one application using its own script:

```bash
bash /opt/fedora-repository/services/bitwarden/install.sh
```

Or select applications through the common installer:

```bash
bash /opt/fedora-repository/install.sh bitwarden rambox
```

To install all available services explicitly:

```bash
bash /opt/fedora-repository/install.sh --all
```

Running the installer without a selection prints usage and does not install
everything. Add `--no-sync` to install code without immediately running
downloads. The installer does not add, remove or change any scheduled job;
configure cron separately as shown below.

The installer:

- Installs runtime dependencies and `/usr/local/bin/rpm-repo-sync`.
- Preserves the server's existing timezone by default.
- Creates `/usr/local/sbin/update-<app>-repo.py` links to the selected services'
  Python entry points. These can be called directly with `/usr/bin/python3`.
- Preserves unselected applications and all existing cron jobs.
- Retains `/root/<app>/update-<app>-repo.sh` as compatibility wrappers; any old
  cron entries using them must be replaced manually.
- Enables Apache folder listings, backs up and disables Fedora's welcome page,
  configures listing/cache options and seven rotated log archives.
- Backs up existing wrappers, root crontab and updater configuration
  under `/root/repo-updater-backup-<UTC timestamp>`.
- Runs a first sync only for the requested repositories. A failed sync returns
  an error and leaves its previous published metadata in place.

Timezone configuration is optional. Cron uses the server's configured local
timezone. To change it deliberately during installation, supply an IANA timezone
name; for example:

```bash
bash /opt/fedora-repository/services/bitwarden/install.sh --timezone UTC
```

With `--timezone`, the installer also backs up the previous timezone and installs
timezone data if needed. Without that option, it does not change `/etc/localtime`
or call `timedatectl`. Updater log timestamps are explicitly in UTC regardless of
the server timezone. Apache is restarted after configuration validation. Cron
is restarted only when an explicit timezone change was requested.

When upgrading the former bundled installation for the first time, the installer
preserves its previously installed services by creating their separate modules.
It reports these migrated services in its output; immediate sync still runs only
for the services explicitly requested. Subsequent selective installs leave other
service modules and schedules alone.

Check the result:

```bash
date '+%Y-%m-%d %H:%M:%S %Z %z'
readlink -f /etc/localtime
crontab -l
find /var/www/html -path '*/Packages/*.rpm' -printf '%f\n'
curl -f http://localhost/bitwarden/repodata/repomd.xml
```

Apache displays filesystem modification times in its local timezone; timezone
changes do not alter the stored file timestamps. Packages copied during
publication have publication-time modification dates, which are not necessarily
the upstream release dates. HTTP date headers continue to use GMT.

### 6. Add the repositories to client machines

Download the definitions for the services you host, replacing `repo.example.com`
with the public endpoint configured above:

```bash
sudo curl -fSL -o /etc/yum.repos.d/bitwarden.repo https://repo.example.com/bitwarden/bitwarden.repo
sudo curl -fSL -o /etc/yum.repos.d/rambox.repo https://repo.example.com/rambox/rambox.repo
sudo curl -fSL -o /etc/yum.repos.d/citrix.repo https://repo.example.com/citrix/citrix.repo
sudo dnf --refresh makecache
```

Install the desired packages using DNF, for example `sudo dnf install bitwarden`.
They then receive updates through the normal `sudo dnf upgrade` workflow. The
server updater does not configure unattended installations on client machines.
Verify the packages advertised by each enabled repository:

```bash
dnf --refresh --repo=bitwarden list --available --showduplicates
dnf --refresh --repo=rambox list --available --showduplicates
dnf --refresh --repo=citrix-workspace list --available --showduplicates
```

## Files and directory layout

| Location | Purpose |
| --- | --- |
| `rpm_repo_sync.py` | Small CLI entry point for the shared engine |
| `common/` | Shared engine, HTTP/model helpers, manifest loading and installation planning |
| `install.sh` | Installs selected service modules and shared dependencies |
| `services/<app>/` | That application's discovery, configuration, installer and Python update script |
| `/usr/local/sbin/update-<app>-repo.py` | Direct Python entry point for that service |
| Root crontab (`crontab -e`) | Administrator-controlled scheduling |
| `examples/myapp/` | Starter service that can be copied and adapted |
| `tests/` | Shared engine, provider discovery, selective installation and integration checks |
| `VALIDATION.md` | Checks completed and test environment limitations |
| `/var/www/html/<app>/<app>.repo` | Client repository configuration served over HTTP |
| `/var/www/html/<app>/Packages/` | Published RPMs |
| `/var/www/html/<app>/repodata/` | Repository metadata, including `repomd.xml` |
| `/usr/local/lib/rpm-repo-sync/rpm_repo_sync.py` | Installed updater code |
| `/usr/local/lib/rpm-repo-sync/common/` | Installed shared engine |
| `/usr/local/lib/rpm-repo-sync/services/<app>/` | Installed module and manifest for that service |
| `/var/lib/rpm-repo-sync/<app>/` | Accepted download state and per-repository lock |
| `/var/www/.rpm-repo-sync-work/` | Private staging, outside Apache's document root |
| `/var/log/rpm-repo-sync/` | Update logs and cron output |

Public RPM filenames are readable and derived from their RPM headers:

```text
ICAClient-26.04.10.1-0.x86_64-0123456789abcdef.rpm
```

The final 16 characters identify the contents using part of the SHA-256 checksum.
Full checksums are still verified. An existing package URL with different bytes
is never overwritten. DNF learns the filenames from metadata, so renaming through
the updater does not change the repository's `baseurl` or the RPM identity.

## Daily updates and maintenance

The installer **never manages scheduling**. There is no schedule in
`service.json`, no cron-file generator and no installed `/etc/cron.d/` file.
Each application has one Python script; decide when to run it in root's crontab.

On the repository server, run as root:

```bash
crontab -e
```

Add these entries for the services you host:

```cron
# Refresh each repository daily; choose times outside backups/maintenance.
0 4 * * * /usr/bin/python3 /usr/local/sbin/update-bitwarden-repo.py
20 4 * * * /usr/bin/python3 /usr/local/sbin/update-citrix-repo.py
40 4 * * * /usr/bin/python3 /usr/local/sbin/update-rambox-repo.py
```

These example times are **04:00, 04:20 and 04:40** in the server's local timezone.
Change the five cron fields directly to change the schedule. Comment out or
remove a line to disable that service. Unlike `/etc/cron.d/` files, a personal
crontab has no `root` user field. View the actual schedule with `crontab -l`.
Changes take effect without reinstalling scripts or restarting cron, and script
upgrades never overwrite them.

When upgrading an older installation, **replace** existing
`/root/<app>/update-<app>-repo.sh` cron lines with the Python entries above rather
than appending duplicate jobs. The installer leaves old jobs unchanged, so they
continue to run at their old times until you edit them. Old manifest
`update_time` keys are ignored. If you manually created separate cron files for
these same jobs, remove their duplicate entries as part of this migration.

Compare the repository server's timezone with the backup host's timezone.
Spacing jobs reduces simultaneous work but does not guarantee the previous job
has finished or detect an overlong backup. The updater retains three versions
per RPM name and architecture and prevents overlapping runs of the same service.

Each script writes a service log under `/var/log/rpm-repo-sync/`. To also capture
console output (including early failures), optionally append a shell redirect:

```cron
0 4 * * * /usr/bin/python3 /usr/local/sbin/update-bitwarden-repo.py >> /var/log/rpm-repo-sync/bitwarden-cron.log 2>&1
```

Run an update or a dry run manually on the server:

```bash
rpm-repo-sync --repo all
rpm-repo-sync --repo citrix
rpm-repo-sync --repo all --dry-run
rpm-repo-sync --list
/usr/bin/python3 /usr/local/sbin/update-bitwarden-repo.py
/usr/bin/python3 /usr/local/sbin/update-citrix-repo.py --dry-run
```

Dry runs can download and validate in staging but do not publish or prune. The
default retention is three versions; Python entry points inherit the CLI default of `--keep 3`.
Locks prevent overlapping runs for the same repository. Unchanged package sets
skip metadata regeneration. Abandoned staging is cleaned on the next run.
`--repo all` operates on services present in the **installed** module directory.
A failure in one service does not stop the remaining services from updating.

```bash
tail -n 50 /var/log/rpm-repo-sync/citrix.log
du -h --max-depth=2 /var/www/html
df -h /var/www/html
systemctl status httpd crond --no-pager
```

Bitwarden uses its official desktop download URL and attempts to obtain an
additional GitHub release digest. Citrix requires the published SHA-256 for each
RPM on its download page. Rambox uses GitHub releases and, when the latest release
has no compatible RPM, selects the newest stable release with one. Betas and
drafts are skipped. Vendor page/API changes can require discovery code updates.

Downloads are retried, checked for completeness and available upstream digests,
and verified with RPM's internal integrity checks. Missing optional Bitwarden or
Rambox digests do not prevent a valid HTTPS download; those checks establish
integrity and do not replace vendor signature verification.

### Select one upstream release for a single run

Rambox supports an exact GitHub release tag, independently of the release
marked "latest":

```bash
/usr/bin/python3 /usr/local/sbin/update-rambox-repo.py --release v3.1.1
```

The shared CLI equivalent is `rpm-repo-sync --repo rambox --release v3.1.1`.
Use the full tag including `v` where the upstream tag includes it. Add
`--dry-run` to validate without publishing; a dry run can still download the RPM.

This flag applies **only to that invocation**. It does not edit cron, service
configuration or store a release pin. The next normal cron run follows GitHub's
"latest" selection and existing stable-RPM fallback again. A newer version that
was mirrored explicitly remains eligible for retention, so a later run finding
an older upstream "latest" does not automatically remove it or downgrade clients.
Future 3.x releases still need an explicit override until the normal upstream
selection points to them.

Only the requested tag is fetched. Missing tags, drafts/prereleases, ambiguous
assets and releases without a compatible RPM fail rather than choosing a
different release. RPM integrity, upstream checksum checks and newest-three
retention remain in effect. Requesting an old release does not force retention
if it falls below the newest three versions already mirrored.

`--release` requires one explicit service; it cannot be used with `--repo all`
or `--list`. Other providers reject it unless they implement the optional
`discover_release(session, config, tag)` function in their own `service.py`.
The common code contains no application-specific release URLs or version rules.

### Update the scripts from GitHub

For an installation cloned under `/opt/fedora-repository`:

```bash
git -C /opt/fedora-repository pull --ff-only
bash /opt/fedora-repository/services/bitwarden/install.sh
```

Use another service's installer to update that service, or use
`bash /opt/fedora-repository/install.sh --all` to update all available modules.

Commit or preserve local edits before pulling. The installer preserves existing
repository definitions and the main virtual host. Existing flat RPMs and older
hash-prefixed filenames migrate automatically after replacement metadata validates.
The separate service modules replace the former standalone download scripts. Original
downloaders already present under `/root/<app>/` are unused after installation;
the installed wrappers call `/usr/local/bin/rpm-repo-sync`.

## Add another service

Start with the included example, outside the installed service directory:

```bash
cd /opt/fedora-repository
cp -a examples/myapp services/myapp
```

The service has these files:

1. **`service.json`** declares its ID, allowed RPM header names and optional
   Fedora dependencies. The ID must match the directory name. Use a
   lowercase ID with letters, digits, `_` or `-`. RPM header names are checked
   without regard to case.
2. **`service.py`** provides `discover(session, config)` and returns a non-empty
   list of `common.models.Asset` objects. Each asset describes a filename, URL,
   allowed package names and, when available, checksum, size and upstream revision.
   This is where vendor-specific HTML/API/redirect handling belongs.
3. **`install.sh`** calls the common installer with that service's ID.
4. **`update.py`** calls the shared engine for that service only; this is the
   entry point to use directly or from cron.
5. **`update.sh`** provides a compatibility shell entry point.

Edit the placeholder vendor URL and RPM names before installation. If you rename
the service, update the directory name, manifest ID and the IDs in both shell
scripts and `update.py`. For multi-package applications, list all allowed RPM
names in the manifest and return the corresponding assets from discovery.

The example resolves the final URL and filename, length, ETag and Last-Modified
headers. A fixed `latest.rpm` URL without a stable revision is deliberately fetched
again each run so new contents are not missed. Prefer a published SHA-256, a
versioned filename and stable revision when the vendor offers them. Do not put
retention, signing or `createrepo_c` calls in the service module.

Then install and verify it independently:

```bash
bash services/myapp/install.sh --no-sync
rpm-repo-sync --list
rpm-repo-sync --repo myapp --dry-run
rpm-repo-sync --repo myapp
```

The placeholder example fails before downloading until you configure a real URL.
Create `/var/www/html/myapp/myapp.repo` with your own `baseurl`, following the
client configuration examples above. Add a schedule yourself with `crontab -e`,
for example `0 5 * * * /usr/bin/python3 /usr/local/sbin/update-myapp-repo.py`.
No changes to the common engine, a central app registry or a hardcoded installer
list are required. The directory under `examples/` is never discovered or installed unless you copy it into `services/` and select it.

## Fedora server upgrades

Use Fedora's packages for Python, `python3-rpm`, Requests, Cronie, Apache and
`createrepo_c`. There is no virtual environment, pip dependency set, pinned
Python version or hardcoded Fedora release number. RPM digest checks and
metadata creation use `rpmkeys` and `createrepo_c`; version comparison uses the
system librpm bindings. Only vendor discovery needs service-specific logic.
The launcher and cron examples use `/usr/bin/python3`, so the distribution
supplies Python and matching RPM bindings together.

Back up `/var/www/html`, `/var/lib/rpm-repo-sync`, `/usr/local/lib/rpm-repo-sync`,
Apache configuration and root's crontab before upgrading. Follow Fedora's
supported upgrade process for your hosting environment. Afterwards verify:

```bash
rpm -q python3 python3-rpm python3-requests rpm createrepo_c cronie httpd
httpd -t
systemctl status httpd crond --no-pager
crontab -l
/usr/bin/python3 /usr/local/sbin/update-bitwarden-repo.py --dry-run
```

Rerun a selected service's installer with `--no-sync` if its dependencies or
entry-point links need restoring. Reinstallation preserves repository data,
state and your crontab. The installer restores standard SELinux labels where
SELinux is active and disables a newly present Fedora welcome page again.

This reduces dependence on a particular Fedora version; compatibility with
all future RPM/Python/Apache versions cannot be guaranteed. Vendor download
pages and client-side RPM dependencies may also change. Check the output and
logs after an upgrade.

## Troubleshooting

**Repository loads, but a package cannot be installed:** inspect DNF's dependency
error. Hosting an RPM does not change its dependencies or supported distributions.
A vendor RPM targeting another distribution may require packages unavailable on
the client. The mirror cannot fix that dependency. Avoid using `--skip-broken` as
a remedy; it skips the package.

**A client requests a removed RPM:** retaining only three versions means older
cached metadata can reference a pruned version. Run the DNF operation with
`--refresh`. The updater retains current and previous metadata objects, but
does not retain every RPM referenced by an old client's cache. After the filename
migration, refresh client metadata before installing or updating.

**Cloudflare serves stale metadata:** the Apache include sets `Cache-Control:
no-store` for `repomd.xml` and `.repo` files. If a Cloudflare cache rule overrides
origin headers, bypass caching for those paths and purge stale entries. Compare
the public URL with the same URL fetched directly from Apache.

**Dates use an unexpected timezone:** check `date` and `readlink -f /etc/localtime`.
The installer preserves the existing timezone unless `--timezone` is supplied.
Apache uses local time for directory listings; updater logs use UTC and HTTP date
headers use GMT. Restart Apache and cron after changing the server timezone.

**Names remain hash-prefixed after upgrading:** check the installer output and
installed updater path. The updated code must be installed and a successful sync
must run before existing filenames migrate. Refresh client metadata afterwards.

**An existing RPM fails validation:** the log names the file. Move that specific
file to a private directory outside `/var/www/html`, then retry. Failed new
downloads are discarded automatically. Do not manually rename public RPMs without
rebuilding their repository metadata.

**Apache serves the Fedora Webserver Test Page:** Fedora's active
`/etc/httpd/conf.d/welcome.conf` can disable the root listing through a
`LocationMatch` rule and display a test page for the resulting forbidden
response. Merely changing `IndexOptions` does not enable listings. Update the
scripts and rerun a selected service's installer with `--no-sync` to apply the
Apache fix without downloading packages. The installer backs up/disables the
welcome configuration and sets `Options +Indexes` and `DirectoryIndex disabled`
for `/var/www/html`. It restores the previous Apache configuration if the syntax
check fails. Existing virtual hosts and repository files are preserved. If the
origin works but the public URL still shows the test page, clear the browser
cache and check any reverse-proxy or Cloudflare cache. For a manual repair, use
the commands in the Apache setup section.

## Backups and rollback

Back up the web root, updater state, installed scripts, Apache configuration and
root crontab on a schedule suitable for the deployment. Use filesystem, VM or
container backups as appropriate for the hosting environment.
The installer's configuration backup is useful for reverting scripts but is not
a full package backup.

Use the exact backup directory printed by the installer to restore the previous
wrappers and root crontab. Restore the saved `installed-updater/` directory to
`/usr/local/lib/rpm-repo-sync/` to revert the common code and service modules,
and restore the saved launcher to `/usr/local/bin/rpm-repo-sync`. To re-enable
Fedora's test page, restore the saved `welcome.conf` to `/etc/httpd/conf.d/`.
Restore the prior Apache include
and timezone as needed, validate Apache, and restart Apache and cron. A full
rollback of pruned package contents requires the container or filesystem backup.

## Validation and documentation

The updater has 61 automated checks, including RPM version ordering, three-version
retention, downloads that fail without pruning history, readable filename
migration, immutable package URLs, metadata validation, locks and unchanged runs.
The suite also checks independent service loading, selective dependencies,
direct Python entry points, symlinks from unrelated working directories,
selective deployment and adding a service without editing the common engine.
See [VALIDATION.md](VALIDATION.md) for the completed checks and environment limits.

To run the tests on Fedora:

```bash
dnf install -y rpm-build python3 python3-rpm python3-requests python3-beautifulsoup4 createrepo_c
cd /opt/fedora-repository
/usr/bin/python3 -m unittest discover -s tests -v
```

Further reading: [createrepo_c](https://github.com/rpm-software-management/createrepo_c),
[DNF5 repository configuration](https://dnf5.readthedocs.io/en/latest/dnf5.conf.5.html),
and [Apache directory listings](https://httpd.apache.org/docs/2.4/mod/mod_autoindex.html).
